## 3. Read-Model Architecture Conclusion

* **Directly Usable Structures (28 / 35)**: Most evaluation, scoring, knockout, and analytics outputs are already serialized as clean, deterministic JSON objects that can be sent directly to the browser.
* **Structures Requiring Server-Side Read Models (7 / 35)**:
  1. `J. Evidence Registry`: Needs field-based index mapping for instant UI hover tooltips.
  2. `K. Derived Metrics`: Needs metadata mapping (friendly display names and categories).
  3. `U. Post-Listing Observations`: Stored in fragmented horizon files; requires chronological timeline aggregation.
  4. `Y. Dataset Membership`: Requires pagination, search, and sorting endpoints.
  5. `Z. Analytics Summary`: Requires decoupled endpoints for KPI summary cards vs detailed charts.
  6. `AH. Current-vs-Proposed Diff`: Requires REST wrapper over `compute_config_diff()`.
  7. `AI. Shadow Evaluation`: Requires REST wrapper over `shadow_evaluate()`.

* **Verdict**: A lightweight **Server-Side Read-Model API (FastAPI)** is required to project these 7 structures without mutating the underlying immutable filesystem records.
